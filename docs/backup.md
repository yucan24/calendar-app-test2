# バックアップと復元

## 保存するもの

追加料金のない、このMacからの暗号化バックアップです。本番 `wswntpyibylcrjjdmguy` とテスト `xvgqwdiyoorzejfozoca` は保存先も接続先も分けます。

| 対象 | 扱い |
| --- | --- |
| 会員・予定・出欠・請求・勤怠・給与調整・収支・銀行照合・意見・回数券の15テーブル | 全列・ID・金額・状態・日時を保存 |
| 名前・4桁コードのハッシュ・会員状態・メール確認状態 | プロフィールと一緒に保存。4桁の平文は保存しない |
| メール送信履歴 | `app_account_notifications` を保存 |
| ログインセッション・再設定リンク・試行制限の3テーブル | 保存・復元しない。復元後は再ログインし、必要な設定メールを再発行 |
| DB構造・関数・権限 | 対応するmigrationのSQL・チェックサム、公開アクセス制限SQLを同梱 |
| Supabaseの管理スキーマ、Auth、Storage、接続キー、SMTPパスワード、Vercel設定 | 対象外。現アプリは独自認証を使用。接続・メール設定は別途管理 |

全データを**一つの読み取り専用SELECT**で取得し、更新中でも同じ時点のスナップショットにします。標準の `db dump` は直接DB接続が必要なため、この環境で接続確認済みの公式Supabase CLI 3.2.0のManagement API経由で取得します。アプリ専用の論理バックアップであり、Supabaseクラスタ全体の複製ではありません。

保存ファイルはAES-256-GCMで暗号化・改ざん検出します。暗号化ファイルをディスクから読み戻し、PGliteへ現行migrationを適用して全16テーブルを復元し、取得元の件数・内容ハッシュと一致したものだけ保存成功にします。新しい列・テーブル・migrationが未対応なら失敗として止めます。

## 保存場所と日常の操作

リポジトリのルートで実行します。Node.js、`npm ci`、対象プロジェクトへのSupabase CLIログインが必要です。`.env.local` は読みません。本番・テストはコマンドで明示します。

```bash
# 本番を今すぐ保存
npm run backup

# 最新の成功・失敗と48時間以内の保存有無を確認
npm run backup:status

# 保存済みの本番ファイルをもう一度復元検証
npm run backup:verify -- --backup '.backups/production/<ファイル名>.nsct-backup'

# テスト環境を保存
node scripts/backup.mjs create --environment test
```

| 場所 | 内容 |
| --- | --- |
| `.backups/production/` | 本番の暗号化ファイル、直近成功・試行記録 |
| `.backups/test/` | テスト環境の暗号化ファイル、記録 |
| `.backup-secrets/backup.key` | 初回に生成する32バイトの復号鍵。画面やログに表示しない |
| `.backups/logs/` | 自動実行の結果。件数・状態のみで、会員情報は記録しない |

フォルダは0700、ファイルは0600で作成し、Git・Vercelから除外しています。鍵が消えた場合、保存ファイルが残っている環境では新しい鍵を自動生成せず止まります。鍵を削除・再生成しないでください。

本番・テストそれぞれ**最新30世代**を保持します。手動保存も1世代です。新しいバックアップの復元確認に失敗したときは古い世代を削除しません。取得結果やDBエラーの詳細は個人情報を含む可能性があるためログに出しません。失敗時の `phase` とその対処は下表を参照してください。

| phase | 確認すること |
| --- | --- |
| `arguments` | コマンド・`--environment`・ファイル指定 |
| `storage` | 保存先の書き込み権限、0700/0600、既存の復号鍵 |
| `schema` | `npm ci` とローカルmigrationの読み込み |
| `remote-read` | ネット接続、公式CLIのログイン期限・対象プロジェクトへの権限。`npx --yes supabase@3.2.0 login` で再ログイン |
| `encrypt` / `publish` | ディスク空き容量・保存先の権限 |
| `restore-rehearsal` | リモートのmigration・列とソースの差、制約違反、取得データの欠落。削除や強制通過はせず、対応するソースで再検証 |
| `retention` | 過去ファイルの削除権限。新しい保存成功ファイルは残る |
| `verify` | 正しい環境・対応する鍵・ファイル破損・対応するソースの版 |

## 自動保存（macOS）

```bash
# 設定内容の表示のみ
npm run backup:schedule -- --print

# 本番の初回保存成功後に登録
npm run backup:schedule -- --install

# 自動保存を停止・登録解除
npm run backup:schedule -- --uninstall
```

ユーザーのLaunchAgent `jp.nsct.calendar.backup` を使います。ログイン時と1時間ごとに確認し、**日本時間でその日の成功分がなければ取得**します。当日の暗号化ファイルが存在し、改ざん検出と保存時のチェックサムが通る場合だけスキップします。失敗した場合は次回の確認で再試行します。

このMacのログイン・起動・通信とCLIの認証が必要です。停止中の日の状態を後日さかのぼって取得することはできません。保存は日単位なので、障害直前までの全変更を保証するものではありません。保存の古さは `npm run backup:status` で確認できます。48時間経過または直近の保存失敗では終了コード1を返します。メールなどの自動通知は送りません。

2026-11-22に、ユーザー指定で**今回はMac内での保存まで**としました。外部サービスへの送信は設定していません。PC故障にも備える場合は、今後、暗号化ファイルと復号鍵をこのMac以外にも保管します。鍵はファイルと別に管理し、どちらもチームで復旧できる保管先に置きます。Mac内の保存だけではPC故障には対応できません。

## 復元の手順

1. 復元したい時点の暗号化ファイル・対応する復号鍵・ソースを用意します。同梱migrationと手元のソースが一致しなければ処理は止まるため、バックアップ時のソースも保管します。
2. まずローカルで検証・SQL作成します。既存の出力先は上書きしません。`--key-file` は鍵を別に保管した場合に指定します。

```bash
node scripts/prepare-backup-restore.mjs \
  --backup '/path/to/file.nsct-backup' \
  --key-file '/path/to/backup.key' \
  --out '.backups/restores/new-directory'
```

3. `localRestore: PASS` と `manifest.json` の環境・取得日時・件数を確認します。出力の `schema.sql` と `restore.sql` は復号済みの会員情報・認証ハッシュを含むため、非公開で扱います。
4. 復元は**別の空のSupabaseプロジェクト**へ行います。現在の本番やテスト環境をリセットしません。新プロジェクトのrefを確認し、SQLを確認してから `schema.sql`、`restore.sql` の順で適用します。新しいプロジェクトの作成・リセット・接続先変更は、この準備コマンドでは実行しません。

```bash
# NEW_PROJECT_REFは復元先の新プロジェクトのrefに置き換える
npx --yes supabase@3.2.0 db query --remote=NEW_PROJECT_REF --yes \
  --file '.backups/restores/new-directory/schema.sql' --output json
npx --yes supabase@3.2.0 db query --remote=NEW_PROJECT_REF --yes \
  --file '.backups/restores/new-directory/restore.sql' --output json
```

`schema.sql` はpublicテーブルやmigration履歴が既にあれば停止します。`restore.sql` は19テーブルをロックし、全テーブルが空であることとmigration・列を照合してから復元し、元データとのハッシュ一致・公開アクセス制限を同じトランザクションで確認します。失敗すればデータはコミットしません。既存請求を削除・合算したり、重複制約を外して通す処理はありません。

5. 復元先でログイン・会員状態・予定・出欠・会計・勤怠を確認し、送信元メール・Supabaseキー・Vercelの接続先を新環境用に設定してから切り替えます。検証中に実メールを送らないようメール送信モードを確認します。復元後は全員再ログインし、未使用の初期設定・再設定リンクは必要に応じて再発行します。
6. 確認後、復号済みSQLは削除します。暗号化ファイルと復号鍵は引き続き非公開で保持します。

## 以前のSupabaseクラスタバックアップ

従来の `.backup.gz` も同じ準備コマンドで読み取れます。この場合は `--key-file` は不要です。`postgres` の既知のpublicテーブルのCOPYデータだけを解析し、クラスタのロール・管理スキーマ・古い関数を実行しません。セッション等の3テーブルは明示的に除外し、それ以外の未知のpublicテーブルはエラーにします。

旧形式では現在のmigration・トリガーで認証を変換するため、平文の4桁コードはハッシュ化されます。出力される `data-insert.sql` は旧データの変換確認用で、既存DBへ安全に上書きするものではありません。現在の暗号化バックアップの復元手順とは区別します。元のDownloadsのファイルは変更しません。

## 検証と参考資料

`npm test` で全テーブルの暗号化往復、実際の復元SQL、4桁の先頭ゼロ、日時の小数秒と時差、権限、セッション失効、鍵違い・改ざん・欠落・重複・既存DBの保護、旧形式CLIを検証します。本番への復元やDBのリセットはテストに含みません。

Supabaseも無料プランでは定期エクスポートと別の場所への保管を推奨しています。[公式のバックアップ説明](https://supabase.com/docs/guides/platform/backups)
